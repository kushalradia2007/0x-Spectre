01 / 04 The Spy's Tool

SSH Tunneling —
Hiding Everything in Port 22

🕵️ The Spy

"Port 22 is open because they need remote administration. They trust it. That trust is my tunnel. I can route any protocol — HTTP, RDP, database connections — through a single SSH connection. From the outside, it all looks like encrypted SSH traffic. The firewall sees one connection. I have everything."

SSH (Secure Shell) was designed as a secure replacement for Telnet — a way to remotely administer servers over an encrypted connection. But SSH has a feature that makes it one of the most powerful evasion tools ever built: port forwarding. It can forward arbitrary TCP connections through its encrypted tunnel, effectively turning a single allowed port into a gateway for any protocol.

There are three types of SSH port forwarding. Each one is a different escape mechanism for a different scenario:

Local Port Forwarding

-L : Tunnel Traffic Out

Forward a local port through SSH to a remote destination

The most common type. ssh -L 8080:internalserver:80 user@jumphost — any connection to your local port 8080 gets tunneled through the SSH connection to internalserver:80. From your browser's perspective, you're visiting localhost:8080. The traffic exits the SSH server and connects to the internal target. Used to access services behind firewalls that block direct connections.

Remote Port Forwarding

-R : Tunnel Traffic In

Forward a remote port through SSH back to a local destination

ssh -R 9090:localhost:3389 user@externalserver — anyone connecting to port 9090 on the external server gets tunneled back through SSH to your local port 3389 (RDP). Used by attackers to maintain reverse access to a compromised internal machine through a firewall that blocks inbound connections — the connection is established outward (allowed), then reversed through the tunnel.

Dynamic Port Forwarding

-D : Full SOCKS Proxy

Create a SOCKS proxy that tunnels all traffic through SSH

ssh -D 1080 user@jumphost creates a SOCKS5 proxy on your local port 1080. Configure your browser or application to use this proxy, and all traffic is tunneled through SSH to the jump host, which forwards it onward. This is the most powerful variant — it's not limited to one port or destination. Any application that supports SOCKS proxies gains full internet access through the encrypted tunnel.

Detection & Defence

How to Catch SSH Tunneling

Deep Packet Inspection and anomaly detection for SSH

SSH traffic is encrypted, making content inspection impossible. But traffic pattern anomalies reveal tunneling: SSH sessions carrying gigabytes of data, connections with high packet counts and unusual timing intervals, or SSH sessions that never terminate. Enterprise firewalls can enforce SSH application proxies that explicitly break and re-establish SSH to prevent arbitrary tunneling. MaxSessions 1 in sshd_config limits multiplexed channels.

The entire Great Escape lab is built around one command:

-D 1080 = SOCKS proxy on port 1080  ·  -N = don't execute remote commands (tunnel only)  ·  -f = run in background. Configure Firefox to use SOCKS5 proxy at 127.0.0.1:1080. All your browser traffic now exits through the jump host, bypassing every firewall rule.

02 / 04 Persistent Tunnels

VPNs — Permanent
Encrypted Pipes

🔴 The Red Teamer

"SSH tunnels die when sessions drop. I need something persistent — something that survives a reboot, reconnects automatically, and generates traffic that looks exactly like everything else. WireGuard. It's 4,000 lines of code. OpenVPN is 70,000. Fewer lines means fewer bugs means fewer ways to detect me."

A VPN (Virtual Private Network) creates a permanent encrypted tunnel between two endpoints — not just for one application, but for all network traffic. Where SSH tunneling is surgical, a VPN is a wholesale relocation of your network identity. All traffic enters the tunnel at one end and exits at the other, completely invisible to anyone observing the connection in between.

WireGuard

Modern · Minimal · Cryptographically Elegant
📦
~4,000 lines of code — auditable by a single developer in an afternoon. OpenVPN is 70,000+. Less code = smaller attack surface.
⚡
State-of-the-art cryptography: ChaCha20 (encryption), Poly1305 (authentication), Curve25519 (key exchange), BLAKE2 (hashing). All modern, all peer-reviewed.
🚀
Kernel-level implementation — runs in the Linux kernel directly, significantly faster than userspace VPNs. 3-5x throughput improvement over OpenVPN.
🤫
Stealth feature: WireGuard only responds to packets containing a valid cryptographic handshake. Port scanners get zero response — the port appears closed to anyone without the key.
⚠️
Uses UDP — may be blocked on restrictive networks that only allow TCP. Static IP assignment requires manual configuration.

OpenVPN

Battle-Tested · Flexible · Widely Supported
🔒
Can run over TCP port 443 — identical to HTTPS traffic. Almost impossible to block without blocking all HTTPS, making it suitable for the most restrictive environments.
🌍
Universal compatibility — supported on every platform, every router, every enterprise VPN gateway. The safest choice for heterogeneous environments.
🔧
Highly configurable — supports certificate-based authentication, LDAP integration, multi-factor authentication, and complex routing policies.
🐌
Slower than WireGuard — userspace implementation with OpenSSL overhead. TLS handshake adds latency. Config files can be 50+ lines for complex setups.
📋
70,000+ lines of code — larger attack surface, historically had more CVEs, but has been extensively audited over two decades of production use.

03 / 04 The Whistleblower's Tool

Covert Channels —
Data Hidden in Plain Sight

📜 The Whistleblower

"They inspect every packet. HTTPS is terminated at the proxy. SSH is blocked. But DNS is open — it has to be, or nothing works. Every device on every network resolves domain names. What they don't check is what's inside the query. I'll put my data in the subdomain field of a DNS TXT lookup. To every IDS in the world, it looks like a misconfigured DNS resolver. It is not."

A covert channel is a communication method that uses a protocol or resource in an unintended way to transmit information. The goal isn't encryption — it's steganography at the protocol level: hiding the fact that communication is happening at all.

DNS tunneling is the most practical covert channel ever devised. DNS (Domain Name System) queries and responses carry a payload field that most networks never inspect. Tools like iodine and dnscat2 encode arbitrary data into DNS subdomain queries — a message becomes a series of lookups like aGVsbG8=.secret.attacker.com. The attacker controls the authoritative DNS server for their domain, which receives the encoded data and responds with encoded replies. Full bidirectional communication through any network that allows DNS.

💡 The Real-World Analogy

Imagine you're smuggling a message out of a prison. Guards inspect every letter — but they're only looking for forbidden content, not the length of each word. You encode your message in the word lengths: "I am okay" = 1-2-4 = dots and dashes. The guards read the letter, find nothing suspicious, and send it through. The recipient counts the letters. DNS tunneling is exactly this — data hidden in the structure of normal-looking queries.

DNS Tunneling

iodine / dnscat2

Encoding arbitrary data inside DNS query subdomains and TXT record responses

The attacker encodes data in base32 or base64 and uses it as the subdomain of a query: aGVsbG8=.c2.attacker.com. The attacker's authoritative DNS server decodes the subdomain and responds with encoded data in the TXT or NULL record. Bandwidth is limited (~1-3 Kbps) but sufficient for shell sessions, small file exfiltration, or C2 (Command & Control) communications. Used in real APT (Advanced Persistent Threat) campaigns including the DNSMessenger malware.

ICMP Tunneling

ptunnel / icmptunnel

Embedding TCP data inside ICMP Echo Request and Reply packets

ICMP ping packets have an arbitrary data payload field. ptunnel encodes TCP connections inside ICMP echo requests/replies. Networks that block all TCP/UDP but allow pings (for monitoring purposes) become usable tunnels. Detection is straightforward — ICMP packets with large, non-standard payloads — but many legacy networks and monitoring tools don't filter on ICMP payload content, making this surprisingly effective in certain environments.

HTTP Tunneling

chisel / HTTPTunnel

Wrapping arbitrary TCP connections inside HTTP or HTTPS requests

On networks that only allow web traffic, tools like chisel establish a WebSocket connection over HTTP/HTTPS and tunnel any TCP protocol through it. From the network's perspective, it's a long-lived HTTPS connection to a web server — completely indistinguishable from normal browser traffic. This is the "allowed protocol wrapper" attack: the container (HTTPS) is trusted, so anything inside it passes.

Detection

Catching Covert Channels

Anomaly detection, DNS monitoring, and DPI for covert channel identification

DNS tunneling leaves statistical fingerprints: unusually long subdomain names (base64 encoded data), high query frequency to a single domain, TXT/NULL record queries (rare in legitimate traffic), and no matching cached responses (every encoded query is unique). Enterprise DNS filtering solutions (Cisco Umbrella, Infoblox) flag these patterns automatically. The defence is DNS analytics, not packet inspection.

04 / 04 The Future

Zero Trust Architecture —
The Perimeter Is Dead

🏛 The Architect

"Every technique in this module assumes something: that if you're inside the network, you're trusted. The VPN gets you inside. The SSH tunnel bypasses the firewall once you're in. DNS tunneling works because internal DNS is trusted. Zero Trust eliminates all of that. There is no inside. There is no perimeter. Every request is authenticated, every time, regardless of where it comes from."

Traditional network security is built on the castle-and-moat model: a hard perimeter, a trusted interior. Everything inside the firewall is assumed to be safe. This model was designed for a world where employees worked at desks in a building, servers lived in on-premise data centres, and "the network" had a clear boundary.

That world is gone. Employees work from coffee shops. Applications live in the cloud. Partners need access to internal systems. Attackers — as every module in this course has demonstrated — routinely get past the perimeter. Once inside, the traditional model gives them enormous freedom to move laterally, escalate privileges, and exfiltrate data. Zero Trust assumes breach has already occurred and requires verification for every single access request.

🏰 Castle & Moat (Traditional)

❌
Trust by location: "You're on the internal network, so you're trusted." VPNs extend this trust remotely.
❌
Implicit trust: Once authenticated once at the perimeter, lateral movement is largely unrestricted.
❌
Binary access: You either have VPN access (everything) or you don't (nothing).
❌
Single failure point: One compromised credential, one phished employee, and the attacker is "trusted."
❌
Invisible users: Once inside, user actions are rarely logged per-resource — broad network access creates massive blind spots.

✅ Zero Trust Network Architecture

✅
Never trust, always verify: Every request is authenticated regardless of source — internal, VPN, cloud, or office.
✅
Least privilege access: Users get access only to the specific application they need, not the entire network. A compromised account reaches one app, not everything.
✅
Continuous verification: Session trust is re-evaluated continuously — device posture, location, behaviour anomalies can trigger step-up authentication mid-session.
✅
Micro-segmentation: Resources are isolated from each other. Lateral movement requires separate authentication for each target — tunneling to "the internal network" yields nothing useful.
✅
Full observability: Every access attempt is logged with user identity, device posture, time, resource, and outcome — complete audit trail for forensics.
🏢 Real-World Zero Trust

Google's BeyondCorp (2014) was the first large-scale ZTNA deployment — after the Operation Aurora breach, Google eliminated their internal network entirely. Every application requires identity verification regardless of whether the user is in a Google office or a café. Cloudflare Access and Zscaler Private Access offer this as a cloud service. The principle: your SSH tunnel into "the network" gets you nothing — each service requires its own authentication, every time.
