📡 Why this module exists — read this first

Right now, as you read this, millions of computers around the world are talking to each other. They're sending emails, loading web pages, streaming videos, and transferring files. And here's the thing nobody tells you when you start learning cybersecurity: most of them are trusting each other blindly.

When your laptop connects to a coffee shop Wi-Fi and loads Gmail, it doesn't actually know it's talking to Google. It believes what it's told. It trusts the network's directions. It follows the rules of a system designed in the 1970s, when the internet was a tiny research project and nobody imagined it would one day carry bank passwords and medical records.

That gap — between what computers assume and what's actually true — is where cybersecurity lives. And the only way to protect a network is to first understand exactly how it works, and exactly how it can be fooled.

This module is your foundation. We won't just memorise dry models. We'll learn each concept by showing you what breaks when it goes wrong. By the end, you'll be able to look at a pile of raw network traffic — thousands of packets of noise — and find the one line that contains a stolen password.

01 / 04 The Foundation

How Networks Are Actually Built

Before we talk about hacking anything, we need to talk about how computer networks are organized. Think of it like this: when you send a letter, there's a whole system involved. You write the letter, put it in an envelope, write an address, hand it to the post office, which puts it on a truck, which drives on a road, which physically exists somewhere. Each of those steps is a separate layer of the delivery process.

Computer networks work the same way. When you click "Send" on an email, that email doesn't just teleport to the recipient. It travels through seven distinct layers of processing, each one responsible for a different part of the job. This layered structure is called the OSI model — Open Systems Interconnection.

The beautiful thing about studying these layers isn't memorizing their names. It's realizing that every single layer can be attacked separately — and knowing which layer is broken tells you immediately what kind of attack you're dealing with.

💡 Real-world analogy

Imagine sending a secret message through a spy network. Layer 7 is you writing the message. Layer 6 is the cipher you use to encode it. Layer 5 is the scheduled meeting time. Layer 4 is the courier service. Layer 3 is the route on the map. Layer 2 is the handshake at the door. Layer 1 is the actual road the courier drives on. An attacker can intercept any of these steps — if they know which layer to target.

How to use this interactive model: Click any row to expand it and see exactly what protocols live at that layer, what a real-world attack looks like there, and how defenders protect it. Every term has a full form. Start at Layer 7 (Application) and work your way down — that's how data travels when you hit "Send."
⚡ The most important thing to understand

Attacks don't respect layers — but defenders must. A SYN flood (which you'll build yourself in Module 3) operates at Layer 4 — Transport, but its effects travel all the way up to Layer 7 — Application, crashing your web server. When an alert fires in your IDS (Intrusion Detection System), knowing which layer generated it tells you immediately what category of attack you're facing.

The Two Systems That Run
Every Network: DNS & DHCP

Before a single useful byte of data travels across the internet, two things have to happen. Your computer needs to know its own address on the network, and it needs to know how to translate human-readable website names into actual machine addresses. These two jobs belong to DHCP and DNS respectively.

Here's why this matters for security: neither DHCP nor DNS was originally designed with authentication. They were created in an era when everyone on the internet was a trusted researcher. Today, both protocols are routinely abused by attackers — and understanding how they work is the first step to understanding how they're exploited.

DHCP

Dynamic Host Configuration Protocol

Automatically assigns IP addresses to devices joining a network

When you connect to a Wi-Fi network, your device doesn't have an IP address yet. It shouts out to the network: "Hello! Anyone out there? I need an IP address!" This is called a DHCP Discover broadcast. The first DHCP server to respond wins — and your device trusts it completely, accepting the IP address, the gateway, and the DNS server it's told to use.

Here's the attack: what if an attacker's machine responds to that broadcast first, pretending to be the DHCP server? Your device would accept a malicious gateway — meaning all your internet traffic now flows through the attacker's machine before going anywhere else. This is the foundation of the rogue DHCP server attack you'll find in today's lab.

DNS

Domain Name System

Translates website names (google.com) into IP addresses computers can understand

Computers don't know what "google.com" means. They only understand IP addresses like 142.250.80.46. DNS is the internet's phone book — you ask it for "google.com" and it tells you the actual address. Your computer then caches that answer so it doesn't have to ask again.

The attack: DNS responses are sent without any verification. An attacker on the same network can intercept your DNS query and respond first with a fake IP address — sending you to their own server instead of Google's. Your browser's address bar would still say "google.com." You'd never know. This is called DNS spoofing, and it's a core component of Man-in-the-Middle attacks (covered in Module 2).

PASSIVE RECON

Passive Reconnaissance

Gathering intelligence about a target without sending any traffic to it

Imagine a burglar who scouts a bank for weeks before the heist — watching guard schedules, photographing entrances, reading news articles about the security system — without ever setting foot inside. That's passive reconnaissance. Zero packets reach the target. They have no idea they're being studied.

In practice, this means using tools like WHOIS (looking up domain ownership records), Shodan (a search engine that indexes internet-connected devices), certificate transparency logs (which reveal all subdomains of a website), and the Wayback Machine (to see old versions of web pages). It's slower, but it's invisible.

ACTIVE RECON

Active Reconnaissance

Probing a target directly by sending packets and analysing the responses

Active reconnaissance is where you go from reading about the bank to actually testing the locks. You send packets directly to the target and analyse what comes back. Tools like Nmap (Network Mapper) let you discover which ports are open, what software is running, and what operating system the target uses — all from the responses to your probes.

The tradeoff: active recon is far more precise and faster, but it leaves logs. Every probe you send is a record of your presence. In an authorised penetration test, this is expected. In an unauthorised attack, it's evidence. In our lab today, you'll use Nmap's output to fingerprint devices.

How Two Computers Say Hello:
The TCP Three-Way Handshake

Every time you open a webpage, send a message, or stream a video over TCP (Transmission Control Protocol), the two computers involved perform a short ritual before any data is sent. This ritual is called the three-way handshake, and it exists to establish that both sides are present, ready, and using synchronized sequence numbers.

Understanding this handshake isn't just trivia — it's the foundation for understanding SYN floods, session hijacking, and port scanning. Each of the three steps below is a real packet. Each one can be forged by an attacker.

Notice that after the server receives a SYN, it allocates memory to track that half-open connection and waits for the final ACK. Now imagine an attacker sends one million SYN packets per second, all with fake source IPs — the server waits for an ACK that never comes, its connection table fills up completely, and it stops accepting new legitimate connections. That's a SYN flood DoS (Denial of Service) attack. You'll build one yourself in Module 3.

02 / 04 Your First Recon Tool

Nmap — Network Mapper:
Seeing in the Dark

Nmap (Network Mapper) is a free, open-source tool created in 1997 by Gordon Lyon (known as "Fyodor"). It's used by everyone from network administrators checking their own infrastructure to security researchers, penetration testers, and — yes — attackers. In fact, Nmap has appeared in multiple Hollywood films including The Matrix Reloaded and Die Hard 4.

At its core, Nmap does one thing: it sends specially crafted packets to a target and analyses the responses to build a picture of that system. Which ports are open? What software is running? What operating system is it? Within seconds, Nmap can give you a complete inventory of an internet-connected machine — without ever logging into it.

Below is a simulated Nmap scan output. Notice what it reveals: not just open ports, but the exact software versions — which can be cross-referenced against public vulnerability databases to find known exploits.

NMAP — NETWORK MAPPER — SIMULATED OUTPUT
$
# -sV = detect service versions  |  -O = detect operating system  |  /24 = scan all 256 addresses in this subnet
Starting Nmap 7.94 ( https://nmap.org ) at 2024-01-15 22:41 Nmap scan report for 192.168.1.1 PORT STATE SERVICE VERSION 22/tcp open ssh OpenSSH 8.9p1 Ubuntu 80/tcp open http nginx 1.22.1 3306/tcp open mysql MySQL 5.7.42 OS detection: Linux 5.4–5.15 (97% confidence)
⚠ Port 3306 (MySQL) is exposed on the LAN with no firewall rule → MySQL 5.7.42 has 12 known CVEs — run: nmap --script vuln -p 3306 192.168.1.1
$
💡 What does "port" mean?

Think of an IP address as a building's street address, and ports as different doors into that building. Port 80 is the front door (web traffic). Port 22 is the service entrance (SSH — Secure Shell, for remote administration). Port 3306 is a back door that should be locked but isn't. An attacker doesn't knock — they try every door until they find one open.

-sS

SYN Stealth Scan

Half-open scan — sends SYN but never completes the handshake

Remember the TCP handshake? Nmap sends the SYN, gets the SYN-ACK back (confirming the port is open), then immediately sends a RST (Reset) to close the connection without completing it. Because the connection was never fully established, many older logging systems never record it. Quieter, faster, default scan type.

-sV

Version Detection

Identifies the exact software version running on each open port

Once Nmap finds open ports, it probes each one with crafted payloads to read the service's "banner" — the greeting message software sends when you connect. A banner saying Apache/2.4.49 is gold for an attacker: they can look up that exact version in the CVE (Common Vulnerabilities and Exposures) database and find a ready-made exploit.

-O

OS Fingerprinting

Identifies the operating system by analysing how it responds to unusual packets

Every OS (Operating System) responds slightly differently to certain types of network packets — different TTL (Time to Live) values, different TCP window sizes, different quirks. Nmap has a database of thousands of these "fingerprints." It sends a series of unusual probes and matches the responses to identify the OS with confidence percentages.

--script

NSE — Nmap Scripting Engine

A built-in scripting framework with 600+ ready-to-run security scripts

NSE is what turns Nmap from a scanner into a full intelligence platform. Scripts can check for known vulnerabilities, default password logins, enumerate users, and much more. --script vuln runs all vulnerability-detection scripts at once — revealing whether a host is unpatched and exploitable.

Lab: The PCAP Treasure Hunt

A PCAP file (Packet Capture) is a recording of all network traffic on a network during a specific time window — every single packet, logged in sequence. Security analysts use tools like Wireshark to open these files and investigate incidents. Think of it as a black-box flight recorder for your network.

You've been handed a PCAP from a corporate network where something suspicious happened. Mission 03 — OS Fingerprinting via TTL

Every packet has a field called TTL — Time to Live. It's a number that starts at a fixed value when the packet is created and decreases by 1 at every router it passes through. When TTL hits zero, the packet is discarded (this prevents packets from looping forever). Each operating system sets a different default starting TTL. By looking at the TTL in a response packet, you can work backwards to estimate what OS sent it.
