01 / 04 Step 1 of the Attack Chain

ARP Poisoning —
Becoming the Invisible Router

Every device on a local network — your laptop, your phone, the printer down the hall — has two addresses. A logical address (an IP address, like 192.168.1.10) that identifies it on the network, and a physical address (a MAC address, like AA:BB:CC:DD:EE:FF) that identifies its actual network hardware. IP addresses can change. MAC addresses are burned into the hardware at manufacture.

When your computer wants to send data to the gateway (your router), it needs to know the router's MAC address. It uses a protocol called ARP — Address Resolution Protocol — to ask. It broadcasts to the entire network: "Hey, who has IP 192.168.1.1? Please tell me your MAC address." The router replies: "That's me — my MAC is 11:22:33:44:55:66." Your computer saves this in a local table called the ARP cache and uses it for all future communication.

Here's the catastrophic design flaw: ARP has absolutely no authentication. Any device on the network can send an ARP reply claiming to be anyone. Your computer will believe it and update its cache immediately — no questions asked. An attacker exploits this by continuously broadcasting fake ARP replies to both the victim and the gateway, telling each one that the attacker's MAC address belongs to the other's IP. Both update their caches. All traffic now flows through the attacker's machine first.

💡 Real-world analogy

Imagine a building with an internal mail system. Every morning, the mail carrier posts an updated list: "Room 101 → Mailbox A, Room 102 → Mailbox B." Now imagine a rogue employee replaces that list with a fake one: "Room 101 → Mailbox A, Room 102 → Mailbox X (the attacker's mailbox)." Everyone keeps sending their letters to the same room numbers — but they all end up in the wrong mailbox first. The attacker reads them, reseals them, and forwards them on. Nobody knows anything went wrong.

⚡ Why This Works Every Time

ARP was designed in 1982 for small, trusted university networks. There was no concept of a malicious insider. The protocol was never updated to require authentication. arpspoof and Ettercap simply exploit this original design decision — one that affects every device on every LAN on earth to this day.

🛡 Defence: Dynamic ARP Inspection (DAI)

Managed switches can enable DAI — Dynamic ARP Inspection, which cross-references every ARP reply against a trusted DHCP binding table. If a reply claims "IP 192.168.1.1 = MAC DE:AD:BE:EF:00:99" but the binding table says the real MAC is different, the switch drops the packet silently. ARP poisoning becomes nearly impossible on networks with DAI enabled.

DNS Spoofing —
The Internet's Lying Phonebook

Once an attacker has positioned themselves in the middle via ARP poisoning, all the victim's traffic flows through them. Most of it is encrypted HTTPS and is unreadable — but DNS queries are almost always unencrypted. Before your browser opens any webpage, it makes a DNS (Domain Name System) query: "What is the IP address of bank.com?" That question travels in plaintext over UDP port 53.

As the man-in-the-middle, the attacker intercepts this query before it reaches the real DNS server. They send back a fake response first: "bank.com is at 192.168.1.99 (the attacker's machine)." The victim's computer caches this lie and connects directly to the attacker's server — which serves a perfect clone of the real website. The victim types their password. The attacker captures it. The victim never notices anything wrong.

This is called a DNS Spoofing attack, and it's why the DNS-over-HTTPS (DoH) standard was eventually developed — encrypting DNS queries so they can't be intercepted in transit.

MitM — Man-in-the-Middle

The Attacker's Position

A class of attacks where the attacker secretly relays and possibly alters communications between two parties

After ARP poisoning, the attacker is positioned between the victim and the gateway. They receive every packet the victim sends, can read or modify it, then forward it — so the victim and server both believe the connection is direct. The attacker is completely invisible. Neither end knows a third party exists.

DNS — Domain Name System

Why DNS is the Perfect Target

The internet's distributed directory service — translates names to IP addresses

DNS was designed to be fast, not secure. It uses UDP (User Datagram Protocol) — a fire-and-forget protocol with no connection or verification. The first valid response a client receives wins. A MitM attacker positioned between the victim and their DNS server can race the real server and inject a fake response in milliseconds.

arpspoof / Ettercap

The Attack Tools

arpspoof: part of the dsniff suite · Ettercap: a comprehensive MitM suite

arpspoof sends continuous fake ARP replies to maintain the poisoned cache (ARP caches expire every few minutes, so the attacker must keep refreshing the lie). Ettercap is a more advanced suite that combines ARP poisoning, traffic interception, and DNS spoofing into a single graphical interface — commonly used in penetration testing labs.

DoH / DNSSEC

Modern Defences

DNS over HTTPS · DNS Security Extensions

DoH (DNS over HTTPS) encrypts DNS queries inside HTTPS connections, making them indistinguishable from normal web traffic and unreadable to a MitM attacker. DNSSEC adds cryptographic signatures to DNS records — the recipient can verify the response came from the authoritative server and hasn't been tampered with. Both are now supported by all major browsers.

02 / 04 The Invisible Downgrade

SSL Stripping —
Making HTTPS Disappear

You might be thinking: "Okay, but what about HTTPS? If the victim's browser uses HTTPS, the attacker can't read the traffic — it's encrypted." This is exactly what most people assume. It's also exactly the assumption that SSL Stripping exploits.

SSL Stripping was first publicly demonstrated by security researcher Moxie Marlinspike at Black Hat 2009. The attack doesn't break encryption — it simply prevents encryption from being established in the first place. Here's how it works:

When you type "bank.com" into your browser (without the https://), your browser first makes a plain HTTP request. The server responds with a redirect: "Please use HTTPS instead." Normally, your browser would follow that redirect and establish an encrypted HTTPS connection. But the attacker, sitting in the middle, intercepts that redirect and strips it. They maintain an encrypted HTTPS connection to the real server themselves — but serve the victim an unencrypted HTTP version of the site. To the server, it looks like the browser is using HTTPS. To the victim's browser, it looks like a normal HTTP page. The padlock is gone. The traffic is plaintext. The attacker reads everything.

🔍 The Victim's Experience

The victim types "bank.com" and lands on what looks like the real bank website. The content is correct. The logo is right. The login form works. The only sign something is wrong is the missing padlock icon in the address bar — and most users have never been taught to check for it. This is why security awareness training matters as much as technical defences.

🛡 Defence: HSTS — HTTP Strict Transport Security

The fix is HSTS (HTTP Strict Transport Security) — a browser policy where a website tells your browser: "Always use HTTPS for this domain. Never accept a plain HTTP connection. Ever." Once your browser receives this instruction (stored locally), it will refuse to connect to that site over HTTP regardless of what any redirect says. SSL Stripping becomes impossible against HSTS-enabled sites. Major banks and all Google services have had HSTS enabled since 2012.
